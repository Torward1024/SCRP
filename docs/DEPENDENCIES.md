# Подключение SCRP и синхронизация

## Обычная сборка

Lock-файл игры содержит `schema_version: 1`, `repository` и `revision`
(40-символьный SHA). Bootstrap `tools/sync_engine.py` входит в игру,
чтобы первая сборка могла получить движок без заранее установленного SCRP.
Канонический bootstrap и его тесты находятся в этом репозитории.

Алгоритм:

1. Явный `--engine-dir`/`SCRP_ENGINE_DIR` включает локальную разработку.
2. Чистый соседний `../SCRP`, совпадающий с lock-файлом, используется напрямую.
3. Иначе создаётся или проверяется `.deps/SCRP` в каталоге игры.
4. Нужный коммит автоматически скачивается, если отсутствует в кэше.
5. Управляемый кэш переключается на этот коммит; чужой origin и локальные
   правки в кэше приводят к ошибке, без перезаписи файлов.

Соседний рабочий репозиторий движка никогда не изменяется автоматически.
Если всё уже есть локально, сборке не нужна сеть. `--offline` запрещает
скачивание и явно сообщает об отсутствующей зависимости.

## Новая версия

Работаем с движком в его собственном checkout, выполняем тесты, публикуем
коммит. Затем в каждой нужной игре запускаем:

```sh
python tools/sync_engine.py --update
```

Команда берёт SHA текущего `main`, обеспечивает checkout этого коммита и
только после этого меняет lock-файл. Самостоятельно тесты игры она не запускает.
Проверяем потребителя и коммитим изменение lock-файла. Игры могут переходить
на новую версию независимо; обычная сборка не меняет их lock-файлы.

## Совместная разработка

```powershell
# В FirstDawn или Scrapheart:
.\build.ps1 -EngineDir E:\Dev\SCRP
```

Так проверяем локальные изменения движка до публикации. Этот режим допускает
другой SHA и незакоммиченные изменения. Для CI и обычных сборок параметр
не задаём: используется только закреплённый коммит.

В CMake явный override — `-DSCRP_ENGINE_DIR=...`; стандартная конфигурация
вызывает bootstrap. В Make Scrapheart — `SCRP_ENGINE_DIR=...`.
